## 简介

该仓库 `nx_open` 中包含了**Network Optix Meta Platform的开源组件**——即用于构建所有基于Nx开发的产品（包括Nx Witness视频管理系统VMS）的源代码与技术规范。

目前，可通过该仓库构建的主要视频管理系统组件是桌面客户端。作为桌面客户端的一部分但也可独立使用的其他重要组件包括Nx Kit库（位于`artifacts/nx_kit/`目录中），详情可参阅其对应的`readme.md`文件。

除文件中另有说明外，此处的大部分源代码及其他文件均遵循 Mozilla Public License 2.0 的许可条款进行授权，相关条款可在该仓库根目录下 `licenses/` 目录中的 `license_mpl2.md` 文件中查看。

注意：本文档仅提供与当前分支相关的、关于构建流程及其前置条件的简要信息。如需了解关于如何搭建构建环境的实际操作指南、构建系统内部原理的详细说明，以及使用构建和开发工具的建议，请参阅该仓库`master`分支中的以下文档：[build.md](https://github.com/networkoptix/nx_open/blob/master/build.md)

## 自由及开源软件声明

“Network Optix Meta Platform开源组件”软件包含了多种免费及开源软件组件，同时依赖于这些组件、与它们交互，或是借助这些组件进行开发。此类组件的完整列表可在[开源软件披露页面](https://meta.nxvms.com/content/libraries/)查看。如需了解更多关于许可、依赖关系、使用方式的信息，以及相关组件的源代码，请访问这些组件的官方网站。

## 构建环境

支持的目标平台与架构：
- Windows 10 x64（Microsoft Visual Studio）。
- Linux Ubuntu 20.04、22.04、24.04（GCC或Clang）x64、ARM 32/64（在Linux x64上进行交叉编译）。
- macOS Monterey 12.6.3（带Clang的Xcode）x64、Apple M1/M2。

构建前提条件：
- **Python 3.8+**——应在`PATH`环境中以`python`的名称存在，对于macOS和Ubuntu系统还需同时存在`python3`这一名称。
- **Pip**——应在`PATH`环境中以`pip`的名称存在，并且需为构建过程中使用的Python解释器安装该工具。
- **CMake、Ninja、Conan**——建议通过`master`分支中的`requirements.txt`文件使用**`pip`**进行安装，所需版本信息可在该文件中查看。
- **Linux系统**：在生成阶段通过CMake指定`cmake`命令行参数`-DinstallSystemRequirements=ON`来安装**构建依赖项和运行时依赖项**（可能需要输入`sudo`密码）。
  - 注意：编译器会在CMake生成阶段作为Conan的构建产物下载——不会使用Linux系统中已安装的编译器（如果有的话）。
- **Windows系统**：Microsoft Visual Studio 2022的[社区版](https://visualstudio.microsoft.com/downloads/)；需选择以下组件：
  - “工作负载”选项卡下的“使用C++的桌面开发”
  - “单个组件”选项卡下的“适用于Windows的C++ CMake工具”
- **macOS系统**：需要**Xcode Command Line Tools 14.2+**；同时还需安装以下**构建依赖项**：
  - 对于Apple M1/M2芯片的Mac，需安装Rosetta 2：
    ```
    /usr/sbin/softwareupdate --install-rosetta --agree-to-license
    ```

## 构建 VMS 桌面客户端

该客户端的 GUI 中使用了一组名为“定制包”的文本与图形元素，它用于定义 VMS 的品牌标识。定制包以 ZIP 文件的形式提供。系统会自动使用 Conan 中预置的默认定制包——此时客户端将显示为 Nx Meta 标识，并带有公司名称、网站地址以及最终用户许可协议文本等占位符。如果您想自定义这些内容，可在 Nx Meta 开发者门户上创建“自定义客户端”实体，然后从 https://meta.nxvms.com/developers/custom-clients/ 下载生成的定制包 ZIP 文件。该页面上也提供非 Nx Meta 标识的定制包选项。

在仓库根目录下，分别有用于 Linux 和 macOS 的 `build.sh` 脚本以及用于 Windows 的 `build.bat` 脚本，其中包含了执行 CMake 配置和构建阶段所需的所有命令。请将这些脚本视为快速入门辅助工具，仔细研究其源代码，同时也可以自由选用您偏好的 C++ 开发工作流程。

这些脚本会将构建目录创建在/用作仓库根目录的同级目录中，并在其名称后添加 `-build` 后缀。此处假设仓库根目录为 `nx_open/`，因此构建目录将为 `nx_open-build/`。

注意：如果因任何原因生成失败，请在下次尝试运行构建脚本之前手动删除 `CMakeCache.txt` 文件。

以下是使用示例，其中 `<build>` 在 Linux 和 macOS 系统中表示 `./build.sh`，在 Windows 系统中表示 `build.bat`。

- 要生成干净的调试版本构建，先删除构建目录（如果存在），然后运行以下命令：
    ```
    <build>
    ```
    编译生成的可执行文件将会被放置在 `nx_open-build/bin/` 中。

- 若要生成包含分发包及单元测试归档文件的纯净发布版构建，可先删除构建目录（如有），然后运行以下命令：
    ```
    <build> -DdeveloperBuild=OFF
    ```
    构建完成的分发包与单元测试归档文件将会被保存在 `nx_open-build/distrib/` 目录中。若需运行单元测试，可解压该单元测试归档文件，然后逐一或并行执行其中的所有可执行文件。

- 若想使用自行准备的定制化包而非 Conan 自带的默认包（带有 Nx-Meta 标识及占位符），可在 `<build>` 脚本中添加以下参数：
    ```
    -DcustomizationPackageFile=<customization.zip>
    ```
    注意：指定压缩包内的 `description.json` 文件中 `"id":` 字段的值必须与服务器上的值一致，才能成功连接。

- 若在进行了某些修改后需要执行增量构建，请直接运行不带参数的 `<build>` 脚本。
    - 注意，在添加/删除源文件或修改构建系统文件后无需手动调用生成阶段，因为 `ninja_tool.py` 会自动处理此类情况——必要时会自动调用生成阶段。

在 Linux 或 macOS 上进行**交叉编译**时，需设置 CMake 变量 `<targetDevice>`：添加参数 `-DtargetDevice=<value>`，其中 <value> 可取以下值之一：
- `linux_x64`
- `linux_arm64`
- `linux_arm32`
- `macos_x64`
- `macos_arm64`

还支持在 Visual Studio IDE 中进行构建和调试：从命令行运行生成阶段，它会创建 `CMakeSettings.json` 和 `launch.vs.json` 文件，随后即可打开该项目。

建议将环境变量 `NX_CONAN_DOWNLOAD_CACHE` 设置为用于存储相关文件的目录的完整路径，这样可以避免在每次执行清理构建时都从互联网上重新下载所有资源；例如，可在仓库根目录及构建目录旁边创建 `conan_cache/` 目录。

## 对可执行文件进行签名

- **Windows**：

    有一个选项可以使用软件发行商证书对构建后的可执行文件（包括分发文件本身）进行签名。要实现这一点，需要一个格式为PKCS#12的有效证书文件。

    签名功能由 `signtool.py` 脚本实现，该脚本是针对原生 Windows 工具 `signtool.exe` 的封装。若要启用签名功能，必须完成以下准备步骤：
- 将发布者证书文件保存在文件系统的某个位置。
- 创建配置文件（建议放在源代码目录之外），该文件必须包含以下字段：
  - `file`：发布者证书文件的路径，可以是绝对路径，也可以是相对于配置文件所在目录的相对路径。
  - `password`：用于保护发布者证书文件的密码。
  - `timestamp_servers`（可选）：受信任的时间戳服务器 URL 列表。如果配置文件中存在此字段，签名后的文件将会使用列表中的某台服务器添加时间戳；若不存在此字段，则签名后的文件不会添加时间戳。

        配置文件的示例可在
        `build_utils/signtool/config/config.yaml` 中找到。
    - 在生成阶段添加一个 CMake 参数 `-DsigntoolConfig=<configuration_file_path>`。如果缺少该参数，则不会进行签名操作。

    您也可以直接调用 `signtool.py` 手动对任意文件进行签名：
    `python build_utils/signtool/signtool.py --config <configuration_file> --file <unsigned_file> --output <signed_file>`

    要测试签名流程，可以使用自签证书。生成此类证书时，可利用 `build_utils/signtool/genkey/genkey_signtool.bat` 这个文件。运行该文件后，它会在执行所在目录中创建 `certificate.p12` 文件以及几个辅助的 `*.pem` 文件。为遵循外部构建的理念，我们建议将这些文件移出源代码目录之外。

- **Linux**：

    无需签名，因此也不提供相关工具或操作指南。

- **macOS**：

    目前正在开发一款适合独立使用的签名工具，未来很可能会提供。暂时您可以采用用于其他 macOS 开发的常规签名流程。

## 运行 VMS 桌面客户端

无需安装任何发行版软件包，即可直接从构建目录运行 VMS 桌面客户端。

构建成功后，Desktop Client 可执行文件会位于 `nx_open-build/bin/` 目录下；其名称可能会因定制包的不同而有所差异。

对于**Linux**和**macOS**系统，直接运行桌面客户端可执行文件即可。

对于**Windows**系统，在运行桌面客户端可执行文件或任何其他已构建的可执行文件之前，需在控制台里运行以下脚本（由Conan在构建过程中生成），该脚本会正确设置PATH及其他一些环境变量：
```
nx_open-build/activate_run.bat
```
若要恢复包括PATH在内的原有变量值，可运行以下脚本：
```
nx_open-build/deactivate_run.bat
```

### 兼容的 VMS 服务器版本

从开源仓库构建的桌面客户端只能连接到兼容的VMS服务器。由于VMS服务器的源代码并未公开，这类服务器只能从各类公开的VMS版本中获得，包括官方发布的VMS版本以及名为Nx Meta VMS的常规预览版本。

对于任何已发布的公共 VMS 版本，只有基于与服务器相同提交版本构建的客户端才能保证兼容性。该特定提交版本可通过仓库中的 git 标签来识别，公共版本的标签格式为 `vms/4.2/12345_release_all` 或 `vms/5.0/34567_beta_meta_R2`。

同一分支中更高版本的提交所构建的客户端，短期内仍可能与已公开发布的服务器保持兼容，但由于源代码的客户端与服务器部分会同步进行某些修改，最终可能会失去兼容性。因此，建议以对应于各公开版本（包括Nx Meta VMS版本）的带标签提交作为客户端修改分支的基准，并在该分支的下一版公开版本发布后尽快对其进行重基。

注意：除了拥有兼容的代码之外，为了能够正常协同工作，客户端与服务器还必须使用具有相同 `<customization_id>` 值的定制化包。

在生成阶段，构建系统会通过检查 git 标签来确定兼容的服务器版本。它会查找当前分支与某个“受保护”分支（对应稳定的 VMS 版本）共有的第一个提交，然后检查该提交是否存在格式为“vms/#.#/#####_...”的“发布”标签。如果未找到此类标签，则构建编号将被设置为 0 并产生警告；否则则从该标签中提取构建编号。若要绕过此算法，可向 cmake 传递“-DbuildNumber=<custom_build_number>”参数；若要恢复默认行为，则需进行全新构建或传递“-DbuildNumber=AUTO”参数。

### VMS 自动更新功能

VMS产品具备完善的自动更新功能，但由于开源版桌面客户端会直接被Nx构建的新版本所覆盖，因此该功能在开源桌面客户端中处于关闭状态。需注意的是，VMS管理员仍然可以强制进行此类自动更新，但将会产生前述后果。

从技术层面来看，可以在 VMS 服务器设置中指定自定义更新服务器，部署该服务器，并按照 VMS 标准准备更新包及元数据，这样即便使用基于开源构建的自定义 VMS，也能实现自动更新功能。未来很可能会提供相关的操作指南和/或工具。
