## はじめに

このリポジトリ `nx_open` には、**Network Optix Meta Platformのオープンソースコンポーネント**が含まれており、これらはNx Witnessビデオ管理システム（VMS）を含むすべてのPowered-by-Nx製品を構築するために使用されるソースコードや仕様です。

現時点で、このリポジトリから構築可能な主要なVMSコンポーネントはDesktop Clientです。Desktop Clientを構成するうえで重要なコンポーネントの中でも、単独で利用できるものとしてNx Kitライブラリ（`artifacts/nx_kit/`）があり、詳細についてはその`readme.md`をご覧ください。

ほとんどのソースコードおよびその他のファイルは、Mozilla Public License 2.0の条件に基づきライセンスされています（ファイル内に別途指定がある場合を除く）。このライセンスの詳細は、リポジトリのルートディレクトリにある`licenses/`ディレクトリ内の`license_mpl2.md`ファイルで確認できます。

注意：本ドキュメントには、現在のブランチに特有のビルドプロセスおよびその前提条件に関する簡単な情報のみが記載されています。ビルド環境の構築方法、ビルドシステムの内部仕組みの説明、そしてビルドおよび開発ツールの利用に関する推奨事項など、より詳細な情報については、このリポジトリの`master`ブランチにある以下のドキュメントを参照してください：  
[build.md](https://github.com/networkoptix/nx_open/blob/master/build.md)

## ビルド環境

対応するターゲットプラットフォームおよびアーキテクチャ：  
- Windows 10 x64（Microsoft Visual Studio）。  
- Linux Ubuntu 20.04、22.04、24.04（GCCまたはClang）x64、ARM 32/64（Linux x64上でのクロスコンパイル）。  
- macOS Monterey 12.6.3（Clangを搭載したXcode）x64、Apple M1/M2。

ビルドに必要な前提条件：  
- **Python 3.8+** – `PATH` 上で `python` として利用可能であること。macOS および Ubuntu の場合は `python3` としても利用可能であること。  
- **Pip** – `PATH` 上で `pip` として利用可能であり、ビルドで使用される Python インタプリタ用にインストールされていること。  
- **CMake、Ninja、Conan** – `master` ブランチの `requirements.txt` から **`pip`** を使ってインストールすることを推奨します。必要なバージョンはこのファイルに記載されています。  
- **Linux:** Generation ステージで `cmake` コマンドライン引数 `-DinstallSystemRequirements=ON` を指定することにより、CMake を通じて**ビルド時および実行時に必要な依存関係**をインストールします（`sudo` パスワードの入力が求められる場合があります）。  
  – 注意：コンパイラは CMake Generation ステージ中に Conan アーティファクトとしてダウンロードされます。Linux システムに既にインストールされているコンパイラ（もしあれば）は使用されません。  
- **Windows:** Microsoft Visual Studio 2022の[Community Edition](https://visualstudio.microsoft.com/downloads/)を使用し、以下のコンポーネントを選択します：  
  - 「The Workload」→「Desktop development with C++」  
  - 「Individual components」→「C++ CMake tools for Windows」  
- **macOS:** **Xcode Command Line Tools 14.2+**をインストールし、さらに以下の**ビルド時に必要な依存関係**もインストールします：  
  - Apple M1/M2 の場合は Rosetta 2 をインストールしてください：  
    ```
    /usr/sbin/softwareupdate --install-rosetta --agree-to-license
    ```

# VMSデスクトップクライアントのビルド

このクライアントのGUIでは、「カスタマイズパッケージ」と呼ばれるテキストやグラフィックの集合が使用されており、これによってVMSのブランディングが定義されます。カスタマイズパッケージはzipファイルとして提供されます。デフォルトのものはConanから取得され、クライアントにはNx Metaというブランド名が表示され、会社名やウェブサイト、エンドユーザーライセンス契約書のテキストといった項目のプレースホルダーが表示されます。これらの項目を自分で定義したい場合は、Nx Meta Developer Portalで「Custom Client」エンティティを作成し、https://meta.nxvms.com/developers/custom-clients/から生成されたカスタマイズパッケージのzipファイルをダウンロードしてください。Nx Meta以外のブランディングを持つカスタマイズパッケージも同じ場所で入手可能です。

CMakeの設定およびビルドを実行するために必要なすべてのコマンドは、リポジトリルートにあるスクリプト`build.sh`（LinuxおよびmacOS向け）および`build.bat`（Windows向け）に記載されています。これらのスクリプトは簡易的なガイドとしてご利用ください。ソースコードを詳しく調べ、代わりにご自身が好むC++開発ワークフローを自由に使用しても構いません。

これらのスクリプトは、リポジトリのルートディレクトリに「-build」というサフィックスを付けて、その兄弟としてビルドディレクトリを作成または使用します。ここではリポジトリのルートが`nx_open/`であると仮定するため、ビルドディレクトリは`nx_open-build/`になります。

注意：何らかの理由で生成に失敗した場合は、次にビルドスクリプトを実行する前に手動で `CMakeCache.txt` を削除してください。

以下に使用例を示します。<build>は、LinuxおよびmacOSでは`./build.sh`、Windowsでは`build.bat`を指します。

- クリーンなデバッグビルドを行うには、ビルドディレクトリ（存在する場合）を削除し、次のコマンドを実行してください：
    ```
    <build>
    ```
    ビルドされた実行ファイルは `nx_open-build/bin/` に保存されます。

- 配布パッケージと単体テストアーカイブを含むクリーンなReleaseビルドを行うには、ビルドディレクトリ（存在する場合）を削除し、次のコマンドを実行してください：
    ```
    <build> -DdeveloperBuild=OFF
    ```
    ビルドされた配布パッケージおよび単体テストアーカイブは `nx_open-build/distrib/` に保存されます。単体テストを実行するには、そのアーカイブを展開し、中に含まれるすべての実行ファイルを順番に、または並行して実行してください。

- Conanから提供されるデフォルトのカスタマイズパッケージ（Nx-Metaブランドでプレースホルダーが含まれている）の代わりに取得したカスタマイズパッケージを使用するには、<build>スクリプトに次の引数を追加してください：
    ```
    -DcustomizationPackageFile=<customization.zip>
    ```
    注意：指定したzipファイル内のdescription.jsonにある「id」フィールドの値は、サーバーに接続できるようにサーバー上の値と一致していなければなりません。

- 変更後にインクリメンタルビルドを実行するには、引数なしで `<build>` スクリプトを実行してください。
    - ソースファイルの追加・削除やビルドシステムファイルの変更後にわざわざ Generation ステージを呼び出す必要はありません。`ninja_tool.py` がこうしたケースを適切に処理するため、必要に応じて自動的に Generation ステージが呼び出されます。

LinuxやmacOS上での**クロスコンパイル**を行う場合は、CMake変数`<targetDevice>`を設定してください。引数`-DtargetDevice=<value>`を追加し、<value>には以下のいずれかを指定します：
- `linux_x64`
- `linux_arm64`
- `linux_arm32`
- `macos_x64`
- `macos_arm64`

Visual Studio IDEでのビルドやデバッグもサポートされています。コマンドラインからGenerationステージを実行すると、`CMakeSettings.json`および`launch.vs.json`が作成され、その後プロジェクトが開かれます。

クリーンビルドのたびにインターネットからすべてのアーティファクトを再ダウンロードするのを避けるため、環境変数`NX_CONAN_DOWNLOAD_CACHE`を使用するディレクトリの完全なパスに設定することを推奨します。例えば、リポジトリのルートやビルドディレクトリの隣に`conan_cache/`というディレクトリを作成してください。

## 実行ファイルの署名

- **Windows**:

    ビルドされた実行ファイル（配布ファイル自体を含む）にソフトウェアパブリッシャーの証明書を使用して署名するオプションがあります。これを実行するには、PKCS#12形式の有効な証明書ファイルが必要です。

    署名処理は、ネイティブなWindowsの`signtool.exe`をラップしたスクリプトである`signtool.py`によって実行されます。署名を有効にするには、以下の準備手順を行う必要があります：
- パブリッシャー証明書ファイルをファイルシステム上のどこかに保存します。
- 設定ファイルを作成します（できればソースツリーの外に）。このファイルには以下のフィールドが含まれていなければなりません：
- `file`：パブリッシャー証明書ファイルのパス。絶対パス、または設定ファイルが存在するディレクトリを基準とした相対パスのいずれかでなければなりません。
- `password`：パブリッシャー証明書ファイルを保護するパスワードです。
- `timestamp_servers`（オプション）：信頼できるタイムスタンプサーバーのURL一覧です。このフィールドが設定ファイルに含まれている場合、署名されたファイルにはリストされているサーバーのいずれかを使用してタイムスタンプが付与されます。このフィールドがない場合、署名されたファイルにはタイムスタンプは付与されません。

        設定ファイルの例は
        `build_utils/signtool/config/config.yaml` にあります。
    - GenerationステージにCMake引数 `-DsigntoolConfig=<configuration_file_path>` を追加してください。この引数が欠落している場合、署名は行われません。

    また、`signtool.py` を直接呼び出すことで任意のファイルに対して手動で署名することもできます：
    `python build_utils/signtool/signtool.py --config <configuration_file> --file <unsigned_file> --output <signed_file>`

    署名処理をテストするには、自己署名証明書を使用できます。このような証明書を生成するには、`build_utils/signtool/genkey/genkey_signtool.bat`というファイルを利用できます。実行すると、実行された同一ディレクトリ内に`certificate.p12`ファイルおよびいくつかの補助的な`*.pem`ファイルが作成されます。ソース外でのビルドという考え方を維持するため、これらのファイルはソースディレクトリの外に移動することを推奨します。

- **Linux**:

    署名は必要ありません。対応するツールや手順も提供されていません。

- **macOS**:

    スタンドアロンで使用できる署名ツールが開発中で、将来的には提供される見込みです。現時点では、他のmacOS向け開発で使用している通常の署名手順をそのまま利用できます。

## VMS Desktop Clientの実行方法

VMS Desktop Clientは、ディストリビューションパッケージをインストールすることなく、ビルドディレクトリから直接実行できます。

ビルドに成功すると、Desktop Clientの実行ファイルは`nx_open-build/bin/`に配置されます。その名前はカスタマイズパッケージによって異なる場合があります。

**Linux**および**macOS**の場合は、Desktop Clientの実行ファイルをそのまま実行してください。

**Windows**の場合、Desktop Clientの実行ファイルやその他にビルドされた実行ファイルを実行する前に、コンソールで以下のスクリプト（ビルド時にConanによって生成される）を実行してください。これによりPATHやその他の環境変数が正しく設定されます：
```
nx_open-build/activate_run.bat
```
PATHを含む元の変数値に復元するには、以下のスクリプトを実行してください：
```
nx_open-build/deactivate_run.bat
```

### 互換性のあるVMSサーバーのバージョン

オープンソースリポジトリからビルドされたデスクトップクライアントは、互換性のあるVMSサーバーにのみ接続できます。VMSサーバーのソースコードは公開されていないため、このようなサーバーは公式のVMSリリースやNx Meta VMSと呼ばれる定期的なプレビューリリースを含む、すべての公開されているVMSリリースからのみ入手可能です。

特定の公開されているVMSリリースにおいて、互換性が保証されるのは、サーバーと同じコミットからビルドされたクライアントのみです。そのコミットはリポジトリ内のgitタグによって識別できます。公開リリースのタグは `vms/4.2/12345_release_all` や `vms/5.0/34567_beta_meta_R2` のような形式になります。

同じブランチ内のより新しいコミットからビルドされたクライアントは、しばらくの間公開されているサーバーとの互換性を維持できるかもしれませんが、ソースコードのクライアント側とサーバー側に同時に導入される変更の影響で、いずれ互換性を失う可能性があります。そのため、Nx Meta VMSリリースを含む公開リリースに対応するタグ付きコミットをベースにクライアントの修正ブランチを作成し、このブランチから次の公開リリースが出るやいなやすぐにリベースすることを推奨します。

注意：互換性のあるコードを持つだけでは不十分で、ClientとServerが正常に連携するためには、同じ `<customization_id>` 値を持つカスタマイズパッケージを使用する必要があります。

生成段階において、ビルドシステムはgitタグをチェックすることで互換性のあるサーバーバージョンを判断しようとします。まず、現在のブランチと「保護された」ブランチのうちの1つ（安定版VMSバージョンに対応するもの）に共通する最初のコミットを探し、「vms/#.#/#####_...」という形式の「release」タグが存在するかを確認します。そのようなタグが見つからない場合、ビルド番号は0に設定されて警告が出力されますが、タグが見つかった場合はそのタグからビルド番号が抽出されます。このアルゴリズムを無視するには、cmakeに「-DbuildNumber=<custom_build_number>」を渡してください。元の動作に戻すには、クリーンビルドを行うか、「-DbuildNumber=AUTO」を渡してください。

### VMSの自動アップデート

VMS製品には包括的な自動更新サポートが備わっていますが、オープンソース版のDesktop Clientではこの機能は無効になっています。というのも、Nxによって構築された新しいバージョンのDesktop Clientで既にカスタマイズされているDesktop Clientを上書きしてしまうからです。ただし、VMS管理者は前述のような弊害が生じるものの、強制的に自動更新を実行させることは可能です。

技術的には、VMSサーバーの設定でカスタムのアップデートサーバーを指定し、カスタムのアップデートサーバーを導入して、VMSの標準に従ってアップデートパッケージやメタ情報を準備することで、オープンソースから構築されたカスタムVMSでも自動更新が機能するようにすることが可能です。将来的には、これを実現するための手順やツールが提供される見込みです。
